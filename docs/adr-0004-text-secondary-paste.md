# 文本次级上屏按处理功能命名

v0.10 把 Shift+Enter 通用化为「次级上屏」入口：图片＝粘贴为图片路径、文件＝粘贴为文件路径（均把路径作为文本上屏，不动条目本体）。文本条目暂无独立次级形态——Shift+Enter 与主上屏等同。按 CONTEXT.md「粘贴为 X」命名族，文本次级入口**按其处理功能命名**（如"粘贴为去空白文本"），本文档记录候选功能与设计约束，供后续版本立项拍板。

## 候选处理功能

按与「本地优先」原则的关系分两级：

**本地确定性处理**（无网络、无外部依赖，不与本地优先冲突）：

- 去空白：去除首尾空白、合并连续空白为单个空格、剔除空行
- 行尾规整：CRLF→LF、去 UTF-8 BOM、去除零宽字符
- Markdown 转纯文本：剥离标记语法保留可读内容

**外部服务处理**（需网络与用户自备的服务凭据，与本地优先冲突）：

- 翻译（翻译服务 API）
- AI 排版 / 润色 / 摘要（LLM API）
- 短链接展开、URL 参数清洗（目标站点请求）

## 与本地优先的冲突决断

FloatPaste 是本地剪贴板工具，处理管道默认不引入网络与第三方。外部服务类功能若做，必须同时满足：

1. **显式开启**：设置页独立开关 + 用户自备 API 凭据（不内置任何服务端），默认关闭
2. **显式触发**：仅经次级上屏入口执行，主上屏（Enter / 单击）永远原样
3. **结果可辨识**：上屏时提示条明示"已用某服务处理"，不留模糊空间
4. **失败回退**：服务不可达或超时时中止上屏并提示，不以原文静默替代（用户意图是"处理后的文本"，静默替代会以错误内容覆盖目标位置）

本地确定性处理不受上述约束，可直接进默认键位。

## 交互形态（核心取舍）

"按处理功能命名"意味着一个处理功能一个入口，多个候选如何选择：

- **方案 A：单一可配置默认处理**——设置页从候选中选一种，Shift+Enter 固定执行它。键盘优先、零额外步骤；换处理需进设置
- **方案 B：Shift+Enter 弹出处理菜单**——按下后列候选二次选择。功能全暴露；多一步交互，且无焦点速贴弹菜单与归还前台的时序冲突（见 no-focus-picker）
- **方案 C：多键位映射**——Ctrl+Shift+Enter 等各绑一种。直达；键位膨胀，与「会话键可自定义」的空间互相挤压

初步倾向 **A**：与速贴「键盘优先、一步到位」的定位一致，可发现性由设置页承担；候选功能增多后再演进 B。

## 开放问题

- 处理结果是否先预览确认再上屏（速贴无焦点形态下预览窗如何呈现）？
- 处理功能是否作用于编辑窗口（保存前处理）还是仅上屏管道？
- 长文本的费用/延迟上限（外部服务类）如何提示？

## Consequences

- 现状：`PasteOption.as_path_text` 承载图片/文件两类路径文本形态，文本类型忽略该标记。文本次级形态立项时该字段需演进为枚举（按处理功能命名族不止"路径文本"一种变体）
